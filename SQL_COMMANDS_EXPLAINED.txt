HERITAGETRAILS - SIMPLE SQL GUIDE
================================

This guide explains the database setup and the path from sample data to a
visitor booking. The database uses MySQL. The two SQL files are schema.sql
and seed.sql.


1. RUN THE SQL FILES
--------------------

Use a new, empty database for this version of the project. By default, the
scripts call it HeritageWalks. These scripts are for a new setup, not for
upgrading an older database. They do not erase data, but schema.sql will
stop if tables already exist. If HeritageWalks already has tables, choose
a different database name and use that same name in schema.sql, seed.sql,
and the DB_NAME setting in .env.

In MySQL Workbench:

1. Open schema.sql and click the lightning bolt to run it.
2. Wait for it to finish. It creates the database tables, travel modes,
   stored procedure, and triggers.
3. Open seed.sql and run it. It adds sixteen Indian cities, 85 landmarks,
   twenty-six tours, route stops, travel options, and sample bookings.
4. In a new query tab, run the checks in section 5.

Run schema.sql before seed.sql because the sample rows need the tables to
exist first. Run schema.sql only once. The seed can be run again to refresh
the sample records and route stops that belong to its fixed ID ranges.


2. WHAT THE TABLES STORE
------------------------

Cities
  One row for each city.

Landmarks
  Places to visit. CityID connects each place to its city.

Itineraries
  The tour routes, their base prices, and their durations.

Itinerary_Stops
  The places on each route. StopOrder sets the visit sequence.

TourModes
  The available options: walking, self-drive car, and tourist bus.

Itinerary_Modes
  The options offered for each route and each option's capacity.

Bookings
  Visitor details, selected route and travel option, date, group size,
  vehicle count, and final price.

A primary key identifies a row. A foreign key links rows in related
tables. For example, a landmark's CityID refers to the city where it is
located. Itinerary_Stops and Itinerary_Modes are bridge tables: they
connect routes to the places and travel options they use.


3. IMPORTANT SQL USED HERE
--------------------------

CREATE DATABASE and CREATE TABLE make the database and its tables.

INSERT INTO adds rows. seed.sql inserts parent data first (the city and
landmarks), then routes and their stops, and finally sample bookings.

SELECT reads data. WHERE filters the rows. ORDER BY sorts the results.

JOIN reads related information from more than one table. For example,
GetItineraryDetails joins a route to its stops, landmarks, and city.

CALL runs the stored procedure named GetItineraryDetails.

The two triggers run automatically when a row is inserted:

  PreventDuplicateLandmark stops the same landmark being added to one
  route twice.

  CheckCapacityConstraint checks the selected route and date. Walking and
  bus options count people/seats; self-drive counts cars.

These are the database checks the application needs. The other SQL blocks
in the schema define tables and the stored procedure/triggers; there are
no old-database migration blocks in this beginner setup.


4. HOW A VISITOR BOOKS A TOUR
-----------------------------

1. The visitor opens Explore Tours. Search can match a city, state, tour,
   historical summary, or landmark name and description. The frontend asks
   the API for available itineraries and travel options.
2. The visitor opens a tour. The API calls GetItineraryDetails to get its
   active stops in StopOrder.
3. The visitor chooses a travel option, date, group size, and enters their
   contact details.
4. The frontend sends those values to the API.
5. The API checks the values, finds the tour price and active landmark
   entry fees, and calculates the group total.
6. The API inserts a row into Bookings. CheckCapacityConstraint checks
   capacity automatically before MySQL accepts the row.
7. The API returns a confirmation. The visitor can use My bookings and the
   same email address to find the reservation later.

The database stores the rules and records. The Node.js API connects the
database to the React frontend.


5. SIMPLE CHECKS IN MYSQL WORKBENCH
-----------------------------------

Select the project database:

  USE HeritageWalks;

List the sample tours:

  SELECT ItineraryID, Title, BasePrice
  FROM Itineraries;

List the cities:

  SELECT Name, State
  FROM Cities;

Show the stops for tour 1 in visit order:

  CALL GetItineraryDetails(1);

List the sample bookings:

  SELECT CustomerName, TravelDate, FinalPrice
  FROM Bookings;

The first query should show twenty-six tours. The city query should show
Mangaluru, Delhi, Jaipur, Agra, Varanasi, Mysuru, Hampi, Kochi, Mumbai,
Kolkata, Chennai, Hyderabad, Ahmedabad, Amritsar, Bengaluru, and Puri. The
procedure should return the ordered stops for Mangaluru Heritage Highlights. The
last query should show the two sample bookings.


6. START THE WEBSITE
--------------------

After running both SQL files:

1. In the project folder, install the backend packages with npm install.
2. Install frontend packages with npm install --prefix frontend.
3. Copy .env.example to .env and enter your MySQL connection details.
4. Run npm run dev from the project folder.
5. Open the frontend address printed in the terminal (usually
   http://localhost:5173).
6. Open a tour, choose a travel option and date, and submit a booking.
7. Use My bookings to look it up by email.

The API normally runs at http://localhost:3001. See README.md for API
details and environment settings.
